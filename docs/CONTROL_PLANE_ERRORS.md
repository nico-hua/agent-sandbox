# 控制面异常处理优化设计

日期：2026-10-20。本文落实本次会话已确认的优化方案。

## 目标和边界

统一异常转换边界、关键任务等待和失败恢复信息。沿用现有 API、SQLite schema 2、模块划分和依赖；保留用户已有工作区修改。HTTP 状态码、错误码、固定文案和诊断 sandbox ID 保持兼容；查询发生主错误时，不再被 client 关闭错误覆盖。资源操作仍仅通过 Docker Runtime，删除前核对精确身份和完整归属标签。

## 职责和数据流

- Runtime/Store 将依赖异常转换为稳定领域/存储异常，保留异常链；事务边界继续兜底清理。
- Service 协调预写、创建、激活、续期和删除，依据明确的创建恢复信息决定是否删除元数据。
- API 集中维护固定响应映射；endpoint 的 503 归并和各只读超时仍由操作上下文决定；未知错误不伪造为某个已知业务错误。
- 共用任务等待基础动作，业务层继续决定取消后补偿及错误优先级。等待结束并取出 worker 结果，不通过忽略事件循环异常规避 Python 3.14 的 shield 报告行为。

## 关键契约

1. 创建取消仅在确认回滚后传播 CancelledError；清理失败或未知结果保留记录和 sandbox ID。删除取消等待关键收尾，续期取消不撤销已提交期限。
2. 创建错误保留现有具体异常作为对外兼容边界；内部补充不可变的阶段、资源状态和脱敏清理问题。Service 不再维护“哪些异常等于已回滚”的类型名单。
3. 资源状态区分未修改、确认回滚、有残留和未知。已登记资源清理成功不能证明丢失响应的创建请求没有产生其它资源；Docker 通信不确定性继续保守处理，不改变既有创建错误响应。
4. 回滚按本次登记资源逆序执行；精确身份的 NotFound 表示已消失，删除响应后复查；归属不符绝不删除。创建回滚删除本次 workspace，正式删除默认保留 workspace。
5. 查询主错误优先于 close 错误；关闭失败只在没有主错误时转换为该查询的稳定领域错误。诊断仅保存固定阶段、资源角色、异常类型等，不输出原始 SQL、路径、凭据或后端响应。
6. Store 读缺失、更新缺失、幂等删除和版本冲突的不同语义不合并。具体异常不为追求数量减少而替换成任意字符串。

## 验收

- 各接口既有错误映射及脱敏回归通过，包含派生异常映射和 endpoint 特例。
- 查询错误与 close 失败叠加时保留主错误；单独关闭失败返回稳定领域错误。
- 各写入阶段首次/重复取消等待最终结果，无额外 shield 异常报告；保留迟到提交、精确版本补偿和未知结果记录。
- 回滚覆盖已消失、归属变化、删除响应丢失及响应成功但资源仍存在，保留结构化清理问题。
- 运行控制面完整默认测试、编译检查和 diff 检查；真实 Docker 集成按环境另行说明，不修改既有开发资源。
